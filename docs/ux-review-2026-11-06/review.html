REL8TION • Independent UX review • 6 November 2026

Make the next useful action unmistakable.

The best retention opportunity is a clear loop from physical Event Pass → successful open house → useful follow-up → next open house. Keep REL8TION's bright sky, navy, human imagery and soft cards. Spend the first changes on reliability, task hierarchy and continuity; a new color palette alone will not create repeat use.

Review and implementation proposal only. No application source, production state, messages, billing, subscriptions, event records or physical devices were changed.

Page-by-page implementation brief

1. App gateway and navigation

Observed: Desktop has a large left headline and a right action panel. At 390 × 844, marketing copy precedes all actions; the final code-entry action sits near the bottom of the first viewport. Main actions measured 58–70 CSS px high, with no horizontal overflow in that state. Sign-in reveals email/password and no visible password-recovery link.

Change: Shorten the hero, replace “Role-aware / Permission-scoped” badges with buyer check-in / disclosure / next-event benefits, and move actions earlier on mobile. Add an actual working access-recovery path beside sign-in. Use “Invited? Open your secure invitation” if the existing button can only instruct people to find their original link. Keep role and permission checks behind every destination. Treat the new shell and legacy field pages as one journey, with explicit Home / Open houses / Visitors / Setup navigation only where those destinations truly work.

2. Claim, onboarding and Event Pass setup

Observed: The context-free claim preview is visually coherent and fits the tested mobile width. Home/office setup repeats “Choose your brokerage to continue.” The location route rendered “Preparing Your Setup”; this review did not establish a successful GPS result. Source includes a 20-second location timeout and address/MLS fallback. Claim listing and agent cards use click handlers on non-button containers.

Change: Remove duplicate instruction banners, identify the current step and explain why location is useful before requesting it. Keep “Search by address or MLS” available during location work, with stale callbacks prevented from overwriting a newer search. Reuse the selected listing rather than asking twice. In onboarding, lead with the device/event status and the next required action; move sales navigation and the second-keychain prompt below the first successful event. Let optional bio/photo work wait.

Preserve: The existing listing-agent authorization and full-screen rejection recovery; selected pass/agent/listing persistence; same-person membership activation; storage fallbacks; physical NFC owner verification. A UI shortcut must never broaden who can host or see buyer data.

3. Reuse and sponsorship choice

Observed in source: The existing full-screen page preserves the selected property and provides two real paths: consented, free event-only sponsorship and catalog-priced membership. It explains permanent-history limits and separate hardware. These are strong foundations, but dense copy makes comparison harder on a phone.

Change: Show two compact, stacked choices with the same rows: Cost / Live dashboard / Recap email / Permanent history / Sponsor visibility. Keep the sponsor identity and event visibility statement beside an unchecked consent box. Show “Start with [name] sponsoring” only after authorization. Membership copy should state current/future permanent records accurately; do not imply upgrading retroactively unlocks sponsored history. Defer the separate hardware explanation to a short expandable note.

4. Owner home and live event dashboard

Proposed order: Current event or next-event action → visitor work requiring attention → event history → profile/setup. Use a compact agent identity strip instead of a 70px-scale name dominating the owner home. Put public-card sharing in a recognizable Share action. Replace “Public QR profile stays public” with an optional, plain-language “Share your business card” explanation.

On the live event screen, keep the property address, event status and last update visible. Collapse property facts and shared-device instructions. Reduce visitor cards to name, arrival, disclosure status, explicitly requested financing help and Call / Text / Details. Move property scenarios into Details so every new visitor does not create a long form. Put End event in a distinct event-management area with confirmation; keep it away from routine visitor actions.

Accuracy checks: “Needs financing” currently counts both not-preapproved buyers and explicit requests; distinguish those labels so interest is never mistaken for consent. The no-LO card routes management to /admin?area=events; ordinary-agent access was not verified, so replace with an authorized assignment/support flow if needed. renderLead() reads state.loanOfficer.loan_officer_phone without optional chaining; verify the no-officer + check-in state before release. This is a source-derived failure risk, not a reproduced production crash.

5. Buyer check-in and closeout

Observed in source: Buyer check-in already contains guided disclosure steps, identity/signature fields, financing choices and distinct notification outcome handling. Do not replace these with a generic lead form.

Change: Add plain progress through contact details, required disclosures and confirmation; preserve back navigation and entered values. Keep required acknowledgments explicit and financing help optional. Test disclosure dialogs with keyboard focus, zoom and mobile document viewing. After completion, distinguish “Check-in saved” from message acceptance or delivery; never encourage resubmission because an SMS failed.

At closeout, show recap destination and confirmed status first, then the event's useful outcomes, then the next event action. For sponsored use, retain email correction/retry recovery and do not close the event before its authoritative recap succeeds. Present the $29 membership and $199 member-only hardware as separate purchases, using the pricing catalog. Do not gate the agent's promised recap behind conversion.

Visual direction: refine the existing identity

The design-system document calls for bright, premium, human, sky/glass/navy styling. The newer gateway adds near-black ink, lime and orange; legacy field screens use bright blue, green, amber and indigo for many different actions. Consolidate these into explicit roles without flattening REL8TION into a generic admin theme.

Give agents a reason to return

Tap physical passRun eventSee useful recapComplete follow-upStart next event

Make return visits about useful work: someone to contact, a recap to use, a document to retrieve, or the next property to activate. Keep the pass reusable and the sponsorship choice reachable. The paid product's enduring value should be organized history and completed work, with hardware supporting field use.

During the eventFresh visitor status, clear disclosure evidence and working contact actions build confidence. Show actual alert states rather than promises.
After the eventRecap first; one obvious next action. For members, a follow-up queue with real persisted state. For sponsored users, the promised recap and eligible next-event sponsorship path.
Before the next eventResume the correct agent/pass context and choose a new verified property. Optional reminders can deep-link to this work after preferences and transport exist.

Notifications are a separate proposal: this review does not establish an agent Web Push pipeline. If built, request permission after a clear value moment, offer event/follow-up preferences, frequency limits and dismissal, and verify device delivery. Avoid generic “come back” prompts and fabricated urgency. No notification or sending setting was enabled by this review.

How to judge improvement

First establish a baseline; no analytics dataset was queried. Compare setup completion and time to first live event, successful recovery after location/access failure, check-in visibility freshness, recap success, and second distinct event use within 30 days. Track members and sponsored agents separately and count distinct open houses rather than resumed sessions. For a new follow-up queue, assess completed useful actions; opening a text composer is not proof of sending. These are proposed evaluation checks, not measured product results.

Implementation sequence and release checks

  1. Trust and field usability: live refresh/status, recovery, semantic controls, labels and button contrast. Verify stale reads retain good data, no duplicate check-ins/messages, keyboard access and small-phone layout.
  2. Task and visual hierarchy: reduce gateway copy, tighten setup steps, move setup below event work, compact visitor cards and clarify sponsor/member comparison. Verify existing NFC/QR and host-authorization routes remain intact.
  3. Return loop: reprioritize closeout and next-event continuation. Build persisted member follow-up work only with its backend, permissions and entitlement checks. Add preference-based notifications only after delivery infrastructure is proven.

Before release, run the repository checks matching touched areas: routes, agent-event assignment, Event Pass activation/security/reuse/mobile and membership/product checks. Use isolated synthetic records and mocked providers. Review 320/390px layouts, 200% zoom, keyboard and screen-reader flow, location denied, storage blocked, no LO, zero check-ins, stale reads, failed recap and canceled checkout. Physical iPhone/Android QR/NFC handoff remains essential field validation.
